# The Android share target hands off through a service worker

Sharing a screenshot into the app from Android's share sheet requires the Web Share Target API, which posts the image as `multipart/form-data` to an action URL declared in the web app manifest. A POST cannot render the app, so something has to receive the file and get the user to a page.

Two mechanisms were available. The server could own `POST /share` directly — natural here, since a FastAPI server already exists and already reads screenshots. Instead a service worker intercepts the POST, stashes the file in the Cache API, and redirects to `/?shared=1`, where ordinary page code picks it up.

The deciding argument is that the screenshot then travels the *same* path a dropped or pasted one travels. The Killer tab (`static/killer.js` at the time, now `web/killer.ts`) already knew how to take a parsed reading and render it, warnings and all — uncaged cells, doubtful sums, the 405 checksum mismatch. The server-side alternative would have had to render a page with the board already loaded, and with it a second copy of that reporting, which would drift. What the two paths now share is a single `applyParsed`.

This also keeps the share path honest about failure: a screenshot that reads badly says so in the same words it would have said them in anyway.

## Consequences

- The worker began as share-handoff only, in an app that cached nothing and could not work offline — the board was reasoned about on the server, so offline would have been a much larger change than it looked. That is no longer true: every engine moved into the browser (`web/sudoku/`, `web/queens/`), which left loading the page as the only thing offline hinting still needed. The worker now also precaches the app shell — the page, its stylesheet, the manifest — and the engine bundle on install and serves them cache-first, so hinting and solving work with no network from the first launch after installation rather than only after a lucky online visit. Offline hinting is deliberate, not a side effect of having a worker around.
- Cache-first with a background revalidation, into a cache named for a version that a deploy bumps: an offline launch is instant and certain, and a new build is picked up on the launch after the one that fetched it. Older caches are deleted on activate, so a deploy does not accumulate in the player's storage. The share stash is deliberately left unversioned — a share can arrive moments before a new worker activates.
- Screenshot reading was the one path a lost connection took away, because the CV reader was server-side, so it had to say so in words rather than surfacing `fetch`'s "Failed to fetch" — see `web/ui/offline.ts`. No screenshot path crosses the network any more: both readers run in the page (`web/reader/`, on the OpenCV.js build in `static/vendor/opencv/`), and so does the choice between them for a shared picture (`web/reader/share-dispatch.ts`), so a screenshot that was dropped, pasted or shared is read on the device and none of the three may blame a connection. The readers' own assets — the runtime and the digit exemplars — are still fetched on the first read and are deliberately not precached, so a first read with no connection does fail; the wording for that is the reader's, not the network's.
- `sw.js` must be served from the root (`app.py` routes it explicitly) — a worker's scope is the directory it is served from, and one under `/static` could not intercept `/share`.
- The form field name `image` is load-bearing across three places: the manifest declares it, Chrome posts under it, and the worker reads it back. It was four while `/share/parse` expected it too; the page reads the stashed file rather than a form field, so the endpoint dropped out of the chain when the dispatch moved. `tests/ui/share-target.test.js` asserts the three agree — the assertion sat in `tests/test_app.py` while one of them was a route, and had to outlive it.
- Changing the share `action` after users have installed the app does not reach existing installs; the share target is registered with the OS at install time and re-registered on reinstall.
- Android only. iOS Safari does not implement share targets, and neither does Firefox for Android.
- One share target must serve two readers, so something decides which by counting cages: the Killer reader runs first, and a picture with fewer than five cages is re-read as a classic board. That rule started as `/share/parse` and now runs in the page, unchanged, in `web/reader/share-dispatch.ts` — moving it was not revisiting it. It remains a reversible choice — a chooser in the UI would do as well — and it is still the piece most likely to want revisiting if a third puzzle type ever accepts screenshots.
