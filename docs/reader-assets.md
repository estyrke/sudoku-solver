# The reader's committed assets

The browser screenshot reader (`web/reader/`) does not render anything at load
time. Two of its inputs are files in the repository, generated by hand and
committed: the digit exemplars it matches against, and the synthetic classic
board its tests read. This page says what they are, why they are committed and
how to regenerate them.

The third committed input, the OpenCV build itself, has its own page:
[docs/opencv-js-build.md](./opencv-js-build.md).

## Why any of this is committed

One reason, and it is the same one every time: `cv2.putText` does not
anti-alias identically across platforms, and classifying a ~16px glyph is
sensitive enough to notice. Rebaking the exemplars on macOS once pushed all
four reference screenshots' cage-sum checksums off 405 (see the comment at the
top of `sudoku/reader/calibrate.py`). Anything rendered per machine would
reintroduce that, so nothing is rendered per machine.

That applies twice over now that two readers have to agree. The Python reader
and the browser reader are held to the same board, cell by cell, by
`tests/test_reader.py` and `tests/reader/classic-board.test.ts` — and a
comparison like that is only meaningful if both are looking at the same pixels.

## `static/reader/glyph-seeds.bin` — the digit exemplars

The exemplars themselves are not produced by this asset. They live in
`sudoku/reader/glyph_seeds.npz`, which stays the source of truth; the asset is a
re-container of exactly those bytes in a form a browser can fetch and parse
without a NumPy reader. Every glyph is copied through unchanged, so running the
script on any machine produces the same file.

```sh
python tools/reader/bake_glyph_seeds.py
```

Format, little-endian:

```
"GLYPHS01"      8 bytes, magic and version
side            u8, the square side of every exemplar (24)
groups          u8, how many digits follow (10)
groups x { digit u8, count u16 }
then, in that order, count x side x side bytes per group
```

Digit 0 is in the file. A Sudoku cell never holds one, but a Killer cage sum
does, so the asset is the whole baked set rather than one reader's slice of it;
`web/reader/read-board.ts` takes the digits 1–9 and leaves the zero out of the
classifier, which is what the Python reader does too.

347 KB uncompressed, and it is fetched on the first read rather than bundled:
it changes only when it is re-baked, so it caches on its own, and a player who
never reads a screenshot never pays for it.

To *change* an exemplar, change `glyph_seeds.npz` — following the procedure in
`sudoku/reader/calibrate.py`, which is careful for good reason — and then
re-bake. Editing the asset directly would make the two readers disagree, which
is the one thing all of this exists to prevent.

## `tests/fixtures/synthetic_classic_board.png` — the classic corpus

There is no screenshot of a real classic Sudoku app in the corpus, so the
classic reader is tested against one rendered board: a printed grid, ten
Givens, one cell of Pencil marks. It used to be rendered by the test itself,
which meant macOS and CI were not running the same test.

Beside it, `tests/fixtures/classic_boards/synthetic_classic_board.json` is the
board the *Python* reader reads from those pixels. Both readers are pinned to
that file. Regenerate both together:

```sh
python tools/reader/render_classic_fixture.py
```

Only do that when the Python reader's read has genuinely changed and the new
read is the correct one — regenerating to make a failing test pass is how a
parity gate stops being one.
